2026-11-13 · Scope: recently changed hot spots in src/still/ · Vocabulary: module, interface, depth, seam, adapter, leverage, locality

This review surfaces architectural friction and proposes deepening opportunities: refactors that turn shallow modules into deep ones. The aim is testability and AI-navigability. It follows the improve-codebase-architecture procedure: scope to hot spots, read GLOSSARY.md and ADRs, apply the deletion test, present ranked candidates, then grill the chosen one.

Scope before the scan

Hot spots. The baseline commit is the whole tree, so the scan weights the modules that carry the most change pressure: cli.py (320 lines, three orchestration loops), execution.py (325 lines, target resolution plus case execution), equivalence.py (171 lines, mixed concerns), and report.py (four output formats).

Domain language. GLOSSARY.md defines contract, case, observation, signature, divergence, counterexample, evidence envelope, behavior lockfile, adapter and verdict. CONTEXT.md and ADR-0001 fix the rule that a verdict describes a bounded corpus. ADR conflict: no candidate reopens ADR-0001; every candidate keeps the disclaimer in the report.

Deletion test. For each suspected shallow unit I asked: would deleting it concentrate complexity, or just move it? A "yes, concentrates" is the signal wanted. A utility whose deletion would duplicate the same three lines in four callers is not a deepening target; it stays.

Ranked candidates

C1 — Deepen the claim module behind one interface

Strong
Files
src/still/cli.py, src/still/equivalence.py, src/still/execution.py, src/still/evidence.py (new), src/still/_worker.py
Problem

Two shallow units split one concept. equivalence.signature_from_observation repeats execution.observation_signature field-for-field, so the "select declared observables" rule has two owners with no locality. The verdict rule and the evidence envelope construction sit as private helpers inside cli.py, where three orchestration loops each reconstruct them. Observation.from_dict is an unused interface, and _worker.py keeps a dead os.getpid() line. Each unit has an interface nearly as wide as its implementation.

Solution

Fold the duplicate signature selection into execution.observation_signature, the one place where Observation lives. Introduce evidence.py as a deep module owning the whole claim: build_envelope(contract, cases, attempted) and classify(divergences, unverified). The three orchestration loops become thin adapters over that seam. Delete the unused interface and the dead line. No declared observable, verdict string, normalizer rule or report field changes.

Benefits
  • Locality: one module owns what a verdict covers; a change to the evidence envelope has one edit site instead of three loops.
  • Leverage: check, lock and replay all consume the same deep interface, so a new output format or a new observable needs no orchestration edit.
  • Depth: a narrow interface (build_envelope, classify) hides the full envelope and verdict semantics; deleting evidence.py would concentrate that complexity back into three loops.
  • Testability: the claim module is pure and directly testable without subprocesses.

C2 — Deepen the case-execution adapter

Worth exploring
Files
src/still/cli.py, src/still/execution.py
Problem

run_check, run_lock and run_replay each repeat the same loop: iterate cases, catch ExecutionError, prefix an unverified reason, track fired normalizers, cap divergences. Three copies of one rule.

Solution

A run_corpus deep module with one interface returning a structured CorpusResult. Risk: lock needs only the before side, replay needs only the after side, so a single function would need a wide options interface and would become shallow itself.

Benefits

High leverage on duplication, but the interface cost is real. Deferred until the still adapter count grows beyond two. Deletion test says "just moves it" today.

C3 — Split report.py into four formatter modules

Speculative
Files
src/still/report.py
Problem

Four renderers in one file can look wide. Deletion test says no: deleting any renderer would move four small functions into four new shallow modules with interfaces as wide as their bodies. report.py already has a narrow interface (render) over a real implementation, which is depth, not shallowness.

Solution

Do not do this. Recorded so a future explorer does not re-suggest it. No ADR needed: the reason is self-evident from the deletion test.

Top recommendation

Tackle C1 first. It has the strongest locality gain, the narrowest interface, and the lowest risk of changing function. C2 waits for a third adapter. C3 is rejected.

Grilling loop (design tree, frontier emptied):

  • Constraints: must keep all four verdict strings, all six observable fields, every declared normalizer name, and every report key unchanged. Recommended answer: yes. Accepted.
  • Dependencies: evidence.py may import model.Contract and report verdict constants; it must not import execution, keeping the seam clean. Accepted.
  • What sits behind the seam: the envelope shape, the verdict classification and the divergence cap. Nothing else. Accepted.
  • What tests survive: all 74 tests, the 17 CLI contract checks, seven deterministic report hashes, and two behavior lockfile replays with --strict. Accepted.
  • Hard gate from the request: no function may change. A lockfile recorded before the edit and replayed after it, plus byte-for-byte report hashes, is the acceptance test. Accepted. Self-verification is circular, so the external fixtures and the full suite sit alongside it.
Conflicts with ADR-0001? None. The disclaimer stays in report.py and in every output format.
